Descripción General

SpidiAgent es un proxy multi-tenant que abstrae la complejidad de la API de SPIDI, permitiendo que tus sistemas y clientes se integren con una API REST simple mientras él maneja toda la lógica de autenticación, rate limiting, reintentos, cifrado y auditoría.

🔐 Multi-tenant

Cada cliente tiene sus propias credenciales SPIDI, agreement IDs y configuración aislada.

📊 Auditoría completa

Cada operación se registra en SQLite con request/response JSON, duración, IP y errores.

🔄 Colas inteligentes

Rate limiting y retry exponencial automático hacia la API de SPIDI.

🔒 Cifrado AES-256

Contraseñas cifradas en reposo con AES-256-GCM + key derivation Argon2.

Filosofía: Tus clientes no necesitan conocer SPIDI. El agente traduce tu API simple a la API compleja de SPIDI.

Seguridad

Cifrado de Contraseñas

Master Key → Argon2id (3 iter, 64MB, 4 threads) → Clave AES-256 → AES-GCM encrypt → base64(salt+nonce+ciphertext)
⚠️ Importante: El master_key debe tener al menos 32 caracteres y guardarse en un secreto seguro. Si se pierde, las contraseñas cifradas no se pueden recuperar.

Autenticación de Tenants

Headers de autenticación
X-Tenant-Key: ak_7f3a9b2c4d5e6f7a8b9c0d1e2f3a4b5c

# O alternativamente:
Authorization: Bearer ak_7f3a9b2c4d5e6f7a8b9c0d1e2f3a4b5c

Protecciones Implementadas

FeatureImplementación
Cifrado en reposoAES-256-GCM con Argon2id KDF
Comparación de contraseñasConstant-time (resistente a timing attacks)
SQL InjectionPrepared statements (database/sql parametrizado)
Rate limitingPor tenant (configurable req/sec)
Concurrencia SQLiteWorker serializado + WAL mode + busy_timeout
Secrets en configSoporta env vars (SPIDI_MASTER_KEY)
Graceful shutdownDrena colas antes de cerrar

Quick Start

1. Compilar

Bash
cd C:\Proyectos\GO\SpidiAgent
set CGO_ENABLED=0
go build -o spidi-agent.exe ./cmd/server

2. Configurar

Bash
copy config.yaml.example config.yaml
# Editar config.yaml con tu master key

3. Iniciar

Bash
set SPIDI_MASTER_KEY=tu-master-key-segura-de-32-caracteres-minimo
spidi-agent.exe

4. Probar

Bash
curl http://localhost:8484/health
¡Listo! El agente está corriendo en el puerto 8484.

Configuración

config.yaml

config.yaml
server:
  host: "0.0.0.0"
  port: 8484
  read_timeout: 30
  write_timeout: 30

database:
  path: "data/spidi.db"
  pool_size: 10

security:
  master_key: "clave-de-32+caracteres-segura"
  rate_limit: 100

logging:
  level: "INFO"
  format: "text"

spidi:
  max_requests_per_sec: 10
  max_retries: 3

Flujo Completo de Pago

1️⃣ Cliente finaliza compra
POST /pagos
{
    "tenant_id": "7f3a9b2c...",
    "monto": 50,
    "moneda": "USD",
    "orden": "ORD-001"
}
⬇️
2️⃣ Agent procesa internamente
  • Valida tenant y API key
  • Obtiene token JWT SPIDI (cacheado)
  • Reutiliza agreement_id del tenant
  • Llama a SPIDI con rate limiting
  • Registra en SQLite (operation_log + sessions)
⬇️
3️⃣ Regresa payment_url
{
    "payment_url": "https://sandbox.mispidi.com/?id=3ddc4cfb...",
    "session_id": "3ddc4cfb..."
}
⬇️
4️⃣ Cliente paga en SPIDI

Rediriges al usuario a la payment_url.

⬇️
5️⃣ Webhook notifica resultado

SPIDI → POST /webhook del agente → POST callback del tenant

⬇️
6️⃣ Confirmas producto/servicio

Tu sistema recibe el webhook y entrega el producto al cliente.

Auditoría

Consultas SQL Útiles

Últimas 10 operaciones de un tenant

SQL
SELECT operation, resource_id, status, duration_ms, created_at
FROM operation_log
WHERE tenant_id = '7f3a9b2c...'
ORDER BY created_at DESC
LIMIT 10;

Operaciones fallidas (últimas 24h)

SQL
SELECT tenant_id, operation, error_message, created_at
FROM operation_log
WHERE status = 'error'
  AND created_at >= datetime('now', '-1 day')
ORDER BY created_at DESC;

Resumen de pagos por estado

SQL
SELECT status, COUNT(*) as total, SUM(amount) as monto_total
FROM sessions
WHERE tenant_id = '7f3a9b2c...'
GROUP BY status;
💡 Tip: Usa DB Browser for SQLite para visualizar la BD gráficamente.

Colas y Concurrencia

Cola de Escrituras SQLite

Todas las escrituras pasan por un worker serializado (canal con buffer 1000).

  • Nunca SQLITE_BUSY
  • Operaciones en orden FIFO
  • Lecturas en paralelo (pool de conexiones)

Cola de Requests a SPIDI

ParámetroDefaultDescripción
max_requests_per_sec10Máximo de requests por segundo
max_retries3Reintentos ante fallo
base_delay500msDelay inicial (se duplica cada retry)

Secuencia de Retry

Intento 1 → falla → delay 500ms → Intento 2 → falla → delay 1s → Intento 3 → falla → delay 2s → Intento 4 → error

Graceful Shutdown

  1. El servidor HTTP deja de aceptar conexiones nuevas
  2. Las conexiones activos terminan gracefully (hasta timeout)
  3. La cola de escrituras se drena (procesa ops pendientes)
  4. La base de datos se cierra limpiamente
Garantía: Ninguna operación en cola se pierde.
